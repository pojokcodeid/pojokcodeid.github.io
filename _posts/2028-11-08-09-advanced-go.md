# Advanced Go

Fase ini membahas lapisan lanjutan: memori dan runtime, profiling/performance,
reflection, embed, build tags, dan stdlib tingkat lanjut.

## Tujuan

- Memahami stack/heap, escape analysis, dan garbage collector.

- Mengenal `reflect` dan `unsafe` beserta trade-off-nya.
- Menggunakan `embed`, build tags, dan cross compilation.

## 1. Memory dan Runtime

### Stack vs heap (konseptual)

```
STACK                                  HEAP
- milik goroutine                      - dikelola garbage collector
- alokasi/dealokasi sangat cepat        - alokasi relatif lambat
- berukuran kecil (default 2→8 KB,      - untuk objek besar / hidup lintas
  tumbuh saat perlu)                      goroutine
- otomatis dilepas saat fungsi selesai  - ditentukan oleh escape analysis
```

### Escape analysis

Go **otomatis** memutuskan apakah suatu nilai harus di-heap atau di-stack.
Kamu bisa melihat keputusannya:

```bash
go build -gcflags='-m' main.go
# ./main.go:12:6: moved to heap: buf
# ./main.go:15:11: string(+) escapes to heap
```

**Pola yang menyebabkan escape ke heap:**

```go
func buatCounter() *int {       // ❌ return pointer → n harus hidup setelah fungsi
	n := 0
	return &n                    // n "escape" ke heap
}

func hitung() int {             // ✅ tetap di stack
	n := 0
	n++
	return n
}

// dikembalikan ke interface{} juga membuat escape
var x any = buatObjek()
```

> **Catatan:** jangan mengoptimasi berdasarkan dugaan — **baca output `-m`**,
> dan pastikan optimasi benar-benar bermakna lewat benchmark.

### Garbage collector

- **Tri-color mark & sweep** concurrent — GC berjalan paralel dengan program.
- **Stop-the-world (STW)** sangat singkat (biasanya < 1ms di Go modern).
- GC aktif bila heap melewati **GOGC** (default 100% = heap tumbuh 2x sebelum GC).
- `GOMEMLIMIT` (Go 1.19+) membatasi memori total — pelindung OOM.

```bash
GOGC=50 go run main.go    # GC lebih agresif (memori lebih hemat, CPU lebih tinggi)
GOGC=off go run main.go    # matikan GC (hanya untuk benchmark!)
GOMEMLIMIT=512MiB ./app    # batas memori soft
```

```go
runtime.SetGCPercent(100)   // setel GOGC dari kode
runtime.SetMemoryLimit(1 << 30) // 1 GiB
```

### Alokasi memory

```go
// cara mengurangi alokasi
var sb strings.Builder   // ✅ builder: alokasi tumbuh bertahap
sb.Grow(1024)            // pralokasi bila tahu ukuran

s := make([]byte, 0, n)  // ✅ pralokasi slice

// ❌ alokasi berulang
func buruk(xs []int) []int {
	var out []int
	for _, x := range xs {
		out = append(out, x*2) // mungkin realokasi beberapa kali
	}
	return out
}

// ✅ alokasi sekali
func baik(xs []int) []int {
	out := make([]int, 0, len(xs))
	for _, x := range xs {
		out = append(out, x*2)
	}
	return out
}
```

### Mengukur alokasi

```bash
go test -bench=. -benchmem ./...
# BenchmarkX-10   1000000   1050 ns/op   256 B/op   4 allocs/op
```

**Metrik penting:**

- `B/op` — bytes dialokasikan per operasi.
- `allocs/op` — jumlah alokasi per operasi.
- **Mengurangi alokasi** = mengurangi tekanan GC = latency lebih stabil.

```bash
# bila perlu tahu SIAPA yang mengalokasi
go test -bench=. -benchmem -memprofile=mem.out ./...
go tool pprof -alloc_objects mem.out
```

### Biaya copying vs pointer

```go
// struct kecil (2-3 field) → pass by value biasanya lebih cepat
type Titik struct{ X, Y float64 } // 16 byte

// struct besar → pointer menghindari salinan
type Rekaman struct { // 1 KB+
	ID      int
	Nama    string
	Riwayat []string
	...
}

// aturan praktis:
// - < ~64 byte dan tidak dimutasi → value
// - besar atau dimutasi → pointer
```

### Profil memori

```go
import _ "net/http/pprof" // atau manual:

f, _ := os.Create("mem.prof")
pprof.WriteHeapProfile(f)
f.Close()
```

```bash
go tool pprof mem.prof
(pprof) top        # fungsi dengan alokasi terbanyak
(pprof) inuse_space # memori yang sedang dipakai
(pprof) alloc_space # total alokasi (termasuk yang sudah dibuang)
```

## 2. Profiling dan Performance

### Benchmark yang valid

```go
func BenchmarkProses(b *testing.B) {
	data := siapkanData() // setup di luar loop diukur

	b.ResetTimer()        // reset timer setelah setup berat
	for i := 0; i < b.N; i++ {
		proses(data)
	}
}
```

**Aturan:**

- Jangan menyertakan setup di dalam pengukuran (`b.ResetTimer`).
- Gunakan `b.RunParallel` untuk pengukuran concurrent.
- Bandingkan **apples-to-apples** (data sama, environment sama).
- Ulangi beberapa kali (`-count=10`) dan lihat variance.

```go
func BenchmarkParallel(b *testing.B) {
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			proses()
		}
	})
}
```

### Menganalisis hasil pprof

```bash
go tool pprof cpu.prof

(pprof) top 30       # lebih banyak
(pprof) web          # grafik (butuh graphviz) → buka di browser
```

**Cara membaca:**

- `cum` = waktu termasuk semua fungsi yang dipanggilnya.

### Memory profiling


### Execution trace

```go
import "runtime/trace"

f, _ := os.Create("trace.out")
trace.Start(f)
defer trace.Stop()
```

```bash
go tool trace trace.out   # membuka visualisasi di browser
```

Trace menunjukkan:

- Kapan tiap goroutine berjalan / menunggu.
- Blocking pada channel, mutex, syscalls.
- GC pauses dan interaksi scheduler.

> **Bedanya:** **pprof** menjawab *"di mana CPU/memori dipakai?"*,
> **trace** menjawab *"apa yang terjadi dari waktu ke waktu?"*
> (berguna untuk latency dan scheduling issue).

### Optimasi berdasarkan data — studi kasus

```go
// SEBELUM: sering alokasi string
func formatLaporan(items []Item) string {
	out := ""
	for _, it := range items {
		out += it.Nama + ": " + strconv.Itoa(it.Harga) + "\n" // alokasi tiap iterasi
	}
	return out
}

// SESUDAH: satu alokasi dengan Builder
func formatLaporan(items []Item) string {
	var sb strings.Builder
	sb.Grow(len(items) * 32)
	for _, it := range items {
		sb.WriteString(it.Nama)
		sb.WriteString(": ")
		sb.WriteString(strconv.Itoa(it.Harga))
		sb.WriteByte('\n')
	}
	return sb.String()
}
```

```bash
# buktikan dengan benchmark:
# before: 1500 ns/op  890 B/op  40 allocs/op
# after:   400 ns/op  210 B/op   1 allocs/op
```

**Proses optimasi yang benar:**

1. **Ukur** (benchmark/profile) — jangan menebak.
2. Temukan **bottleneck nyata** (biasanya 80% waktu di 20% kode).
3. Ubah **satu hal**.
4. **Ukur lagi** — bila tidak membaik, kembalikan.
5. Ulangi.

## 3. Reflection dan Low-level

### Package `reflect`

Reflection = membaca/memodifikasi struktur data **saat runtime** tanpa tipe statis.

```go
package main

import (
	"fmt"
	"reflect"
)

func main() {
	var x float64 = 3.14

	v := reflect.ValueOf(x) // Value — "kotak" berisi nilai + tipenya
	fmt.Println(v.Type())   // float64
	fmt.Println(v.Kind())   // float64

	// memodifikasi: butuh pointer!
	vp := reflect.ValueOf(&x).Elem()
	vp.SetFloat(2.71)
	fmt.Println(x) // 2.71

	// bekerja dengan struct
	type User struct {
		Nama string
		Age  int
	}
	u := User{"Budi", 30}
	uv := reflect.ValueOf(u)
	for i := 0; i < uv.NumField(); i++ {
		fmt.Println(uv.Type().Field(i).Name, uv.Field(i))
	}
}
```

**Konsep penting:**

- `reflect.ValueOf` mengambil **nilai**; untuk mengubah, harus lewat **pointer**.
- `reflect.Type` = informasi tipe; `reflect.Value` = nilai yang dibungkus.
- **Zero Value** tidak bisa di-set — harus `Elem()` dari pointer.

### Kapan reflection berguna

- **JSON/serialization** (`encoding/json` memakai reflect untuk struct tag).
- **ORM** dan mapping database.
- **Framework** yang butuh binding field berdasarkan tag.
- **CLI** yang membangun flag dari struct.
- **Validasi** berbasis tag (`binding:"required"`).

### Trade-off reflection

| Aspek | Keterangan |
|-------|-----------|
| Kecepatan | 10-100x lebih lambat dari akses langsung |
| Type safety | Tidak ada — error baru muncul saat runtime |
| Keterbacaan | Kode jadi lebih sulit dipahami |
| Optimasi compiler | Terbatas (inlining tidak berlaku) |

```go
// ❌ pakai reflect tanpa perlu — lambat dan rawan error runtime
func Ambil(nama string, obj any) any {
	v := reflect.ValueOf(obj)
	return v.FieldByName(nama).Interface() // panic bila field tidak ada
}

// ✅ alternatif statis
func AmbilNama(u User) string { return u.Nama }
```

**Prinsip:** pakai reflect **hanya** bila tidak ada cara statis — dan
sembunyikan di dalam abstraksi (seperti yang dilakukan stdlib).

### `unsafe` (pengenalan dan risiko)

```go
import "unsafe"

// 1. melihat ukuran dan offset
type S struct {
	A bool  // offset 0
	B int64 // offset 8 (padding!)
	C bool  // offset 16
}
fmt.Println(unsafe.Sizeof(S{})) // 24

// 2. konversi slice byte → string TANPA copy (hemat memori)
func bytesToString(b []byte) string {
	return unsafe.String(unsafe.SliceData(b), len(b))
}

// 3. string → bytes (⚠️ JANGAN menulis hasilnya!)
func stringToBytes(s string) []byte {
	return unsafe.Slice(unsafe.StringData(s), len(s))
}
```

**Risiko `unsafe`:**

- Melanggar **jaminan type safety** Go.
- Bisa menyebabkan **memory corruption** dan crash.
- **Tidak kompatibel** dengan GC bila dipakai salah.
- Kode bisa **tidak jalan** di versi Go berikutnya.
- Race detector dan tool analisis mungkin tidak membantu.

> **Aturan:** hindari `unsafe` kecuali ada **bukti profil** bahwa copy menjadi
> bottleneck. `unsafe.String`/`unsafe.Slice` (Go 1.20+) relatif aman untuk
> konversi read-only — tapi tetap pertimbangkan `string(b)` yang aman dulu.

### `embed` — menanam file ke binary

```go
package main

import (
	"embed"
	"fmt"
	"net/http"
)

// Prasyarat: file & folder berikut harus ada sebelum build:
//   echo "1.0.0" > VERSION
//   mkdir -p static templates && echo "<h1>halo</h1>" > static/index.html
//   echo "{{.Judul}}" > templates/index.tmpl
//go:embed static/*
var staticFS embed.FS

//go:embed VERSION
var versi string

//go:embed templates/*.tmpl
var templates embed.FS

func main() {
	// tanpa file eksternal — binary sudah berisi semua aset
	http.Handle("/static/", http.FileServer(http.FS(staticFS)))
	fmt.Println("versi:", versi)
}
```

**Keuntungan:**

- Satu binary = deployment sederhana (tidak perlu membawa folder aset).
- Aset tidak bisa "tertinggal" atau beda versi dengan binary.
- Mendukung file, folder, dan embed ke `string`/`[]byte`.

**Batasan:**

- File harus di dalam folder package (tidak bisa `../`).
- Ikut ter-embed saat **build** — tidak bisa diubah tanpa rebuild.

### Build tags

```go
//go:build linux && amd64
// hanya build di Linux untuk arsitektur amd64

func hanyaLinux() {}
```

Satu file hanya boleh punya **satu** blok `//go:build` (gabungkan kondisi
dengan `&&` / `||`), dan komentar penjelas ditulis di baris terpisah.
Pilihan constraint lain (masing-masing di file berbeda):

```go
//go:build !windows
// semua OS kecuali Windows
```

```go
//go:build integration
// diaktifkan hanya saat: go build -tags integration
```

```bash
go build -tags integration ./...   # aktifkan tag saat build
```

**Kegunaan:**

- **Platform-specific** implementasi (`file_linux.go`, `file_windows.go` —
  suffix `_GOOS`/`_GOARCH` juga otomatis jadi build constraint).
- Memisahkan **test integration** dari unit test.
- Fitur eksperimental / konfigurasi build.

```bash
# file dengan suffix otomatis difilter:
file_linux.go    # hanya di-build di Linux
file_darwin.go   # hanya di macOS
```

### Cross compilation

```bash
# build untuk Linux dari macOS/Windows — TANPA CGO, langsung jalan
GOOS=linux GOARCH=amd64 go build -o app-linux .

# Windows
GOOS=windows GOARCH=amd64 go build -o app.exe .

# ARM64 (Apple Silicon / Raspberry Pi)
GOOS=linux GOARCH=arm64 go build -o app-arm64 .

# cek semua kombinasi
go tool dist list
```

> **Catatan:** proyek yang memakai **cgo** (binding C/C++, mis. driver
> database berbasis cgo) butuh toolchain lintas platform. Pakai dependensi
> **murni Go** agar cross-compile mulus dengan `CGO_ENABLED=0`.

```bash
CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o app .
```

- `-trimpath` — hapus path lokal dari binary (reproducible + aman).
- `-ldflags="-s -w"` — strip symbol & DWARF (binary lebih kecil).

### CGO dasar (opsional)

CGO memungkinkan memanggil library C:

```go
// #include <stdio.h>
// void hello() { printf("hello from C\n"); }
import "C"
```

**Trade-off:**

- ❌ Cross-compile jauh lebih rumit.
- ❌ Binary lebih besar, startup lebih lambat (inisialisasi runtime).
- ❌ Interop C bisa memicu data race yang tak terdeteksi GC.
- ✅ Diperlukan bila memakai library C (SQLite lama, OpenSSL, dll).

> Kebanyakan kebutuhan CGO di Go modern bisa dihindari dengan library murni Go.

```go
tr := &http.Transport{
```

### 3. CLI dengan subcommand dan konfigurasi

```go
package main

import (
	"flag"
	"fmt"
	"os"
)

// versi & commit diisi lewat -ldflags saat build (lihat fase 11)
var (
	versi  = "dev"
	commit = "none"
)

// serve & migrate = fungsi aplikasi; di sini hanya ilustrasi alur CLI
func serve(addr, cfgPath string) { fmt.Println("serve:", addr, cfgPath) }
func migrate(direction string)    { fmt.Println("migrate:", direction) }

func main() {
	if len(os.Args) < 2 {
		fmt.Println("usage: tool <serve|migrate|version>")
		os.Exit(1)
	}

	switch os.Args[1] {
	case "serve":
		fs := flag.NewFlagSet("serve", flag.ExitOnError)
		addr := fs.String("addr", ":8080", "alamat listen")
		cfgPath := fs.String("config", "config.yaml", "path config")
		_ = fs.Parse(os.Args[2:])
		serve(*addr, *cfgPath)

	case "migrate":
		fs := flag.NewFlagSet("migrate", flag.ExitOnError)
		direction := fs.String("dir", "up", "up|down")
		_ = fs.Parse(os.Args[2:])
		migrate(*direction)

	case "version":
		fmt.Printf("app %s (build %s)\n", versi, commit)

	default:
		fmt.Println("command tidak dikenal:", os.Args[1])
		os.Exit(1)
	}
}
```

### 4. Aplikasi dengan graceful shutdown

Gabungkan `signal.NotifyContext` + `srv.Shutdown` + penutupan resource:

```go
func main() {
	ctx, stop := signal.NotifyContext(context.Background(),
		os.Interrupt, syscall.SIGTERM)
	defer stop()

	db := bukaDB()
	defer db.Close()

	srv := &http.Server{Addr: ":8080", Handler: mux}
	go func() {
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)
		}
	}()

	<-ctx.Done()
	log.Println("shutdown dimulai")

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	if err := srv.Shutdown(shutdownCtx); err != nil {
		log.Printf("dipaksa berhenti: %v", err)
	}
	// db.Close() dieksekusi oleh defer
	log.Println("bersih")
}
```
